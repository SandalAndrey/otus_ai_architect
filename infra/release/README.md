# Реестр выпуска

Единица выпуска - связка из четырёх артефактов: код, веса, индекс, промпты.
Выкатить их по отдельности нельзя, они согласованы между собой. Здесь
хранятся записи реестра: по одной на выпуск, именем служит идентификатор
выпуска.

Обоснование неразделимости - [ADR-0020](../../docs/adr/0020-release-strategy-canary-by-audience.md)
и [ADR-0012](../../docs/adr/0012-no-feature-store-indexing-serving-consistency.md):
расхождение между преобразованиями на индексации и в онлайн-пути уже опознано в
проекте как дефект, и выпуск кода отдельно от индекса - прямой способ его
получить.

**Состояние: записей нет.** Единственный файл здесь -
[`example.yaml`](example.yaml), образец формата. Записи появляются, когда
заработает полный гейт (работа 4.4 плана работ): запись создаётся его
последним шагом, вручную не пишется.

## Зачем это нужно

Три применения, и каждое отвечает на вопрос, на который иначе ответа нет.

**Разбор инцидента.** По записи восстанавливается, какой код на каких весах и
на какой версии индекса отвечал пользователю в конкретный день. Без этого
"ответ был неверный" не отличается от "ответ был верный для той версии
каталога".

**Откат.** Поле `supersedes` указывает версию, которая держится горячей 72 часа
после полного переключения, - то есть то, куда откатываться.

**Сравнение канарейки с базой.** Поле `release` становится меткой на всех
метриках. Обе версии отвечают на одни и те же вопросы, с одного хоста, в одну
секунду; разделить их иначе нечем.

## Правила

- Запись неизменяема. Исправление выпуска - новая запись, а не правка старой.
- Одновременно в метриках живут не более двух значений `release`. Прежнее
  удаляется через 72 часа после завершения выпуска, вместе с выводом горячей
  копии. Иначе каждый выпуск даёт постоянный прирост числа временных рядов.
- Лицензия весов фиксируется вместе с версией: смена весов без проверки
  лицензии невозможна технически, а не по регламенту.
- Отчёты гейтов лежат в объектном хранилище, в записи - только ссылки и
  итоговые значения.
