## 1. Инфраструктура как код

### 1.1. Что поднимается на этапе 1

По [ADR-0009](adr/0009-llm-hosting-self-hosted-on-rented-gpu.md) этап 1 - это
один арендованный хост с GPU и замкнутый контур на нём. Kubernetes на одном
узле даёт накладные расходы без единой выгоды, которой он платит: ни
масштабирования, ни отказоустойчивости узла, ни сложной маршрутизации здесь
нет. Поэтому код инфраструктуры делится на два уровня: Terraform поднимает
облачные ресурсы, cloud-init и Compose разворачивают на них стек.

Фрагменты ниже - сокращённые выдержки из
[`infra/terraform/main.tf`](../infra/terraform/main.tf), который **ни разу не
применялся**: модуль `./modules/minio` не написан, значения переменных не
заданы. Файл фиксирует состав ресурсов и принятые решения, см. раздел 5.

```hcl
# Провайдер облака. Регион - РФ: NFR-3.5 требует хранения на территории РФ.
provider "yandex" {
  zone = "ru-central1-a"
}

# Сеть: публичная подсеть только под обратный прокси,
# служебная - под хранилища и сервис инференса. Сегментация из NFR-3.
resource "yandex_vpc_network" "core" { name = "assistant-net" }

resource "yandex_vpc_subnet" "edge" {
  name           = "edge"
  network_id     = yandex_vpc_network.core.id
  v4_cidr_blocks = ["10.10.1.0/24"]
}

resource "yandex_vpc_subnet" "internal" {
  name           = "internal"
  network_id     = yandex_vpc_network.core.id
  v4_cidr_blocks = ["10.10.2.0/24"]
  # Выхода в интернет нет: закрытый контур обеспечивается маршрутизацией,
  # а не договорённостью не обращаться к внешним API.
}

# Узел инференса. Конфигурация из ADR-0019: A100 40 ГБ, Qwen3-14B в INT4.
resource "yandex_compute_instance" "inference" {
  name        = "assistant-gpu"
  platform_id = "gpu-standard-v3"
  zone        = "ru-central1-a"

  resources {
    cores         = 8
    memory        = 96
    gpus          = 1
  }

  boot_disk {
    initialize_params {
      image_id = var.gpu_image_id   # образ с драйверами и CUDA
      size     = 200                # веса моделей и кэш образов
      type     = "network-ssd"
    }
  }

  secondary_disk {
    disk_id = yandex_compute_disk.data.id   # хранилища и озеро
  }

  network_interface {
    subnet_id = yandex_vpc_subnet.internal.id
    nat       = false
  }

  metadata = {
    user-data = file("cloud-init.yaml")     # ставит Docker и поднимает Compose
  }
}

# Объектное хранилище: зоны озера из ADR-0011 плюс телеметрия Tempo.
# На этапе 1 это MinIO внутри контура, бакеты создаются одним модулем.
module "object_storage" {
  source  = "./modules/minio"
  buckets = ["bronze", "silver", "gold", "traces", "backups"]

  # Bronze хранит оригиналы байт в байт и закупочные цены:
  # версионирование включено, доступ - только конвейеру.
  versioning  = { bronze = true, silver = false, gold = false }
  retention   = { traces = "30d", backups = "90d" }
}

# Секреты в состоянии Terraform не хранятся: только ссылки на хранилище.
resource "yandex_lockbox_secret" "app" { name = "assistant-secrets" }
```

Три решения в этом коде существеннее самого кода.

**Выход в интернет отсутствует на уровне маршрутизации.** Требование закрытого
контура из NFR-3 записано в проекте с самого начала, но до этого документа оно
держалось на том, что в коде нет обращений к внешним API. Это не механизм, а
намерение: достаточно одной библиотеки, которая пойдёт за обновлением. Отсутствие
NAT у служебной подсети делает требование проверяемым.

**Состояние Terraform хранится в объектном хранилище с блокировкой**, а не
локально у инженера. Иначе два применения подряд с разных машин расходятся, и
инфраструктура перестаёт описываться кодом фактически, оставаясь описанной
формально.

**Секретов в коде нет.** Terraform создаёт секрет и права на него, значения
кладутся отдельно. Состояние Terraform содержит значения ресурсов в открытом
виде, и секрет, записанный переменной, окажется в состоянии.

### 1.2. Стек на узле

```yaml
# docker-compose.yml, сокращённо. Полный - в infra/.
services:
  proxy:        # обратный прокси: вход, веса канарейки, закрепление сессии
  app:          # приложение и агенты, образ с тегом = хеш коммита
  vllm:         # сервис инференса, профиль B из NFR-1
  neo4j:        # граф знаний
  qdrant:       # векторный индекс
  minio:        # озеро и хранилище трасс
  dagster:      # оркестратор конвейера знаний
  otel:         # сбор телеметрии
  prometheus:   # метрики
  tempo:        # трассы, поверх minio
  grafana:      # панели и алерты
```

Версии образов закреплены тегами, а не `latest`: иначе перезапуск контейнера
меняет версию без следа в истории.

### 1.3. Целевая установка и условия перехода

Отказ от Kubernetes - решение этапа 1, а не принцип. Целевая схема описывается
сейчас, чтобы переход не оказался переписыванием с нуля.

| Что меняется | Проект этапа 1 | Целевая схема |
| --- | --- | --- |
| Оркестрация | Compose на одном узле | Managed Kubernetes, группа узлов с GPU |
| Объектное хранилище | MinIO в контуре | Оно же: облачный S3 нарушил бы закрытый контур |
| Маршрутизация | Вес на обратном прокси | Ingress плюс штатный разбор трафика |
| Инференс | Один контейнер vLLM | Группа подов с автомасштабированием по очереди |
| Секреты | Хранилище облака | Оно же, через внешний контроллер секретов |

Условия перехода, любое из двух: нагрузка превышает возможности одной карты по
расчёту из [ADR-0019](adr/0019-model-size-bounded-by-memory-bandwidth.md), либо
появляется второй инференс-узел для выпусков со сменой весов. Переход до этого
момента - накладные расходы без выгоды, и записывать его в план работ этапа 1
значит завышать смету.

Переносимость обеспечивается тем, что приложение упаковано в образы и не
зависит от способа их запуска. Compose-файл при переходе заменяется на чарт;
код приложения, конвейер CI и состав гейтов не меняются.

## 2. Конвейер поставки кода

Схема - [`delivery-cicd.png`](diagrams/delivery-cicd.png).

| Этап | Что делает | Срабатывает | Время |
| --- | --- | --- | --- |
| Линтер и типы | Статический разбор, проверка символов в документации | Каждый коммит | Секунды |
| Модульные тесты | Нормализация наименований, чанкинг, разбор прайсов | Каждый коммит | Минуты |
| Сборка образа | Тег - хеш коммита, сканирование зависимостей | Каждый коммит в запрос на слияние | Минуты |
| Стенд | Та же сборка, уменьшенный корпус | После сборки | Минуты |
| Быстрый гейт | 15 канареек, формат ответа, фильтр по грифу, наличие источника | На стенде | Минуты |
| Сквозные тесты | Четыре роли, проверка отказа по правам | После быстрого гейта | Минуты |
| Полный гейт | Ragas на золотом датасете, сравнение с прошлым выпуском | Перед выпуском, в окне GPU | Часы |

Состав гейтов и их разделение по времени - из
[14-test-plan](14-test-plan.md), раздел 2.1; замер стоимости судьи - из
[ADR-0014](adr/0014-quality-gate-and-judge-strategy.md).

**Проверка символов в линтере** - не придирка к оформлению. В проекте принято
писать документацию только основными символами клавиатуры; правило, которое
проверяется глазами, нарушается на третьей неделе. Автоматическая проверка
стоит секунду.

**Раннер внутри контура.** Облачный исключён: судьёй служит локальная модель, и
золотой датасет за периметр не уходит. Версия интерпретатора на раннере
закреплена явно - Ragas тянет зависимости, которые отстают от свежих версий
Python, и обновление интерпретатора способно уронить оценку, не затронув наш
код. Это не предположение: на замере стоимости судьи так и произошло.

### 2.1. Ручных действий ровно два

| Действие | Кто | Почему не автоматизировано |
| --- | --- | --- |
| Слияние в main | Ревьюер | Решение о содержании изменения. Автоматическое слияние по зелёным проверкам означает, что код не читают |
| Старт выпуска | Дежурный | Выбор момента: выпуск не начинают в пятницу вечером и в часы пиковой нагрузки |

Всё остальное - сборка, проверки, развёртывание на стенде, продвижение по
ступеням, откат по жёсткому сигналу - выполняется без участия человека.
Единственное исключение в сторону ручного действия: отказ судьи на полном гейте
разбирается инженером, потому что судья ошибается
([ADR-0014](adr/0014-quality-gate-and-judge-strategy.md)).

## 3. Конвейер знаний и его стык с поставкой кода

Схема - [`delivery-mlops.png`](diagrams/delivery-mlops.png).

**Обучения модели в проекте нет.** Это записано в
[13-data-pipeline](13-data-pipeline.md) и повторено в
[15-observability](15-observability.md): модели не обучаются и не дообучаются,
разделения train/val нет, дрейфовать нечему. Типовая цепочка MLOps "обновился
датасет - переобучение - реестр моделей - выпуск" у нас принимает вид:

| Типовой шаг | Что на его месте у нас |
| --- | --- |
| Обновился датасет | Пришла партия: прайс поставщика, выгрузка каталога, PDF |
| Триггер оркестратора | Dagster по появлению объекта в bronze либо по расписанию |
| Переобучение | Переиндексация: разбор, извлечение сущностей, векторизация |
| Проверки обучения | Great Expectations на границах зон плюс проверки готовности индекса |
| Реестр моделей | Реестр версий индекса плюс хранилище весов |
| Запуск выпуска | Быстрый гейт на новой коллекции, затем смена псевдонима |

Подмена не косметическая. В обучаемой системе артефакт - файл весов, и его
качество меряется на отложенной выборке. У нас артефакт - коллекция векторов и
граф, а качество меряется тем же золотым датасетом, что и качество кода. Отсюда
следует вывод, вокруг которого построен весь раздел: **индекс и код нельзя
выпускать по отдельности**.

### 3.1. Единица выпуска - связка из четырёх артефактов, а не отдельный образ

| Составляющая | Чем версионируется |
| --- | --- |
| Код приложения | Хеш коммита, он же тег образа |
| Веса моделей | Версия и хеш файла, лицензия |
| Индекс | Мажор и минор коллекции, `ingest_run_id` |
| Промпты и схемы агентов | Версия в репозитории, внутри образа |

Реестр выпуска хранит эти четыре идентификатора вместе с отчётами обоих гейтов.
По записи реестра восстанавливается, какой код на каких весах и на какой версии
индекса отвечал пользователю в конкретный день, - это условие разбора
инцидента, а не удобство.

Запись реестра - один файл на выпуск, каталог
[`infra/release/`](../infra/release/). Записей там пока нет: они создаются
последним шагом полного гейта, вручную не пишутся. Лежит только образец формата
([`example.yaml`](../infra/release/example.yaml)), сокращённо:

```yaml
release: "2026-11-14-a7f3c21"      # значение метки release в метриках

code:
  image: "registry.internal/assistant:a7f3c21"
  commit: "a7f3c21e94..."
  prompts_version: "1.4"           # лежит внутри образа

weights:
  llm:      { name: "Qwen3-14B", quant: "INT4", sha256: "...", license: "Apache-2.0" }
  embedder: { name: "bge-m3",            sha256: "...", license: "MIT" }
  reranker: { name: "bge-reranker-v2-m3", sha256: "...", license: "Apache-2.0" }

index:
  collection: "catalog_v4_2"       # псевдоним переключается на неё
  major: 4                         # сверяется онлайн-путём до поиска, ADR-0012
  minor: 2
  ingest_run_id: "dagster-2026-11-13-0417"

gates:
  fast: { passed: true, canaries: "15/15", report: "s3://gold/gates/..." }
  full: { passed: true, faithfulness: 0.86, relevancy: 0.91, delta: -0.01 }

supersedes: "2026-10-30-3c1b8d9"   # версия, которая держится горячей 72 часа
```

Поле `release` здесь не декоративное: его значение становится меткой на всех
метриках, и по нему канарейка отделяется от базы (раздел 4.3).

Основание для неразделимости - [ADR-0012](adr/0012-no-feature-store-indexing-serving-consistency.md):
расхождение между преобразованиями на индексации и в онлайн-пути уже опознано в
проекте как дефект, и выпуск кода отдельно от индекса - прямой способ его
получить. Онлайн-путь поэтому сверяет мажорную версию коллекции до поиска, а не
после.

### 3.2. Смена весов - отдельный случай

Веса меняются не потому, что их переобучили, а потому, что вышла новая версия
модели или решено заменить эмбеддер. Для проекта это самый дорогой вид выпуска:

- Смена эмбеддера обесценивает весь индекс - векторы несопоставимы, нужна
  полная переиндексация, а не инкрементальная.
- Смена весов LLM требует полного гейта: канареечные промпты и датасет
  прогоняются заново, потому что поведение меняется целиком.
- Канарейки для весов нет: две модели в карте делят полосу памяти пополам, и
  скорость падает со 108 до 54 токенов в секунду на поток при требуемых 90.
  Расчёт и следствия - [ADR-0020](adr/0020-release-strategy-canary-by-audience.md).

Поэтому смена весов выполняется blue-green в окне плановых работ за счёт
бюджета ошибок, а не канареечно.

## 4. Стратегия выпуска

Схема - [`delivery-canary.png`](diagrams/delivery-canary.png), обоснование -
[ADR-0020](adr/0020-release-strategy-canary-by-audience.md).

### 4.1. Почему лестница не 1 - 5 - 100

При 30 000 запросов в месяц это около 1000 запросов в сутки. Один процент -
десять запросов: ступень, на которой нечего измерять и остаётся только ждать.
Поэтому лестница строится иначе.

| Ступень | Аудитория | Запросов в сутки | Условие перехода |
| --- | --- | --- | --- |
| 0. Тень | Никто, ответы не отдаются | - | 200 запросов, окно GPU |
| 1. Внутренний контур | Все сотрудники | по факту | 100 запросов и 1 рабочий день |
| 2. Публичный, 5 процентов сессий | Покупатели | около 50 | 200 запросов и 2 рабочих дня |
| 3. Публичный, 25 процентов сессий | Покупатели | около 250 | 500 запросов и 2 рабочих дня |
| 4. Публичный, 100 процентов | Все | 1000 | Прежняя версия горячей 72 часа |

Первая ступень - аудитория, а не доля: сотрудники сообщают о странном ответе
словами, а не метрикой, и сто их запросов информативнее тысячи анонимных.

Условие перехода - число запросов **и** время одновременно. Запросы без времени
могут набраться за утренний всплеск и не показать вечернего профиля; время без
запросов не проверяет ничего.

### 4.2. Как переключается трафик

Доля задаётся весом в конфигурации обратного прокси, развёртывание - той же
командой, что и обычное. Сессия закрепляется за версией по хешу идентификатора
диалога.

Закрепление обязательно: по NFR-1.6 диалог хранит до 60 обменов контекста, и
сессия, перескочившая между версиями на середине, получит ответ, не связанный с
предыдущим. Пользователь увидит дефект продукта, а не аккуратный выпуск.

Service mesh не ставится: на одном хосте с четырьмя контейнерами он добавил бы
задержку в бюджет 5 секунд и слой, который некому сопровождать.

### 4.3. Метрики отката

**Жёсткие сигналы: порог ноль, откат автоматический.** Эти метрики в исправной
системе равны нулю всегда, поэтому вердикт выносится по одному событию и не
требует ни сравнения с базой, ни набора статистики.

| Сигнал | Метрика | Основание |
| --- | --- | --- |
| Ответ без ссылки на источник | `answers_without_citation_total` | NFR-2.4 |
| Утечка атрибутов закрытого грифа | `acl_leak_total` | NFR-3.1, блокирующий критерий приёмки |
| Расхождение мажорной версии индекса | `index_version_mismatch_total{severity="major"}` | ADR-0012 |

**Сравнительные сигналы: порог относительно базы в том же окне.**

| Сигнал | Условие отката |
| --- | --- |
| Внутренние ошибки и таймауты | 3 и более на канарейке при нуле на базе |
| Доля отказов | Превышение базы вдвое при не менее чем 50 запросах |
| Ответы без сверки | Доля выше 3 процентов, порог ADR-0010 |

База измеряется одновременно с канарейкой, а не по вчерашним значениям. В этом
единственное статистическое преимущество канарейки на малом объёме: суточный
профиль, состав вопросов и состояние железа у двух версий общие.

**Условие, без которого это не работает: метка `release` на каждой метрике.**
Обе версии отвечают на одни и те же вопросы, с одного хоста, в одну секунду, -
разделить их иначе нечем. Значение метки берётся из поля `release` записи
реестра выпуска, и сравнение выглядит так:

```promql
sum by (release) (rate(assistant_errors_total{type=~"internal|timeout"}[15m]))
  / sum by (release) (rate(assistant_requests_total[15m]))
```

Метка вводится вместе с реестром выпуска, до первой ступени лестницы, а не
вместе со ступенями 2 и 3. В первой редакции документа о наблюдаемости она была
записана среди отложенного - это ошибка: без неё механизм отката не работает
ни на одной ступени, включая первую.

Цена метки - рост числа временных рядов. Ограничивается правилом: одновременно
живут не более двух значений `release`, прежнее удаляется через 72 часа после
завершения выпуска, вместе с выводом горячей копии. Без правила каждый выпуск
даёт постоянный прирост кардинальности.

**Сигналы удержания: продвижение запрещено, откат не запускается.**

| Сигнал | Почему не откат |
| --- | --- |
| Задержка p95 выше 5 с | Набирается от 200 запросов; на ступени 1 недостоверна |
| Рост доли деградации | По NFR-6 деградация штатна, а не отказ |

**Что сигналом не является.** Метрики судьи - faithfulness и answer relevancy -
в продуктиве не считаются: судья стоит десятки секунд на пару. Их место -
полный гейт до выпуска ([ADR-0014](adr/0014-quality-gate-and-judge-strategy.md)).

### 4.4. Откат

| Что откатывается | Как | Время |
| --- | --- | --- |
| Код и промпты | Вес канарейки в ноль, прежний образ уже запущен | Секунды |
| Индекс | Обратная смена псевдонима коллекции | Секунды |
| Веса модели | Возврат прежней версии и перезапуск инференса | Единицы минут, цена - холодный старт |

Прежняя версия держится горячей 72 часа после полного переключения. Срок
выбран так, чтобы пережить выходные: дефект, проявляющийся на редком классе
вопросов, за двое суток может не встретиться.

**Файлы есть, работающего конвейера нет.** В репозитории лежат скелеты:

| Файл | Состояние |

Скелеты зафиксированы раньше кода намеренно: решения о сегментации сети, о
способе хранения состояния Terraform и о том, что попадает в образ, дешевле
принять до написания приложения, чем подгонять под него. Код появляется с
работы 3.1 плана работ.

Работающее задание конвейера - проверка символов в документации. Выбрано не
случайно: в проекте принято писать только основными символами клавиатуры, а
правило, которое проверяется глазами, нарушается на третьей неделе.

Таблица ниже отвечает на вопрос "входит ли механизм в объём работ этапа 1", а
не "сделан ли он".

| Механизм | Объём этапа 1 | Основание |
| --- | --- | --- |
| Terraform и cloud-init для узла и хранилищ | Входит | Работа 3.1 |
| Конвейер CI с обоими гейтами | Входит | Работы 4.1 и 4.4 |
| Реестр выпуска как связка | Входит | Записи в метаданных, часов почти не требует |
| Метка `release` на метриках | Входит | Предусловие сравнения канарейки с базой |
| Blue-green индекса сменой псевдонима | Входит | Предусмотрен ADR-0012, работа 3.3 |
| Ступени 1 и 4 лестницы | Входит | Опирается на разделение контуров из НФТ |

| Автоматический откат по жёстким сигналам | Отложено | Алерты описаны, автоматизация действия - нет |

Смета этапа 1 не пересматривается: то, что входит в объём, опирается на уже
заложенные работы.

**Следует назвать своим именем.** Когда ступени 2 и 3 будут отложены при
реализации, лестница сведётся к внутреннему контуру и полному переключению, то
есть окажется ближе к blue-green, чем к канарейке. И отдельно: наличие файлов в
`infra/` не делает конвейер работающим. Скелет фиксирует решения, а не
проверяет их; проверка начинается с первого `terraform apply` на работе 3.1.

### 5.1. Порядок реализации

Зависимости между частями задают порядок, и нарушать его нельзя.

| Шаг | Что делается | Почему раньше следующего |
| --- | --- | --- |
| 1 | Dockerfile, Compose, Terraform, cloud-init | Без воспроизводимой среды гейты негде исполнять |
| 2 | Конвейер CI: линтер, тесты, сборка, стенд | Без стенда гейты нечем кормить |
| 3 | Реестр выпуска и метка `release` на метриках | Без них нечего сравнивать и не из чего восстанавливать состав выпуска |
| 4 | Быстрый гейт, затем полный | Полный требует окна GPU, быстрый - нет |
| 5 | Ступени 1 и 4 лестницы | Опираются на все предыдущие шаги |

Шаг 3 часто пытаются отложить "до первой канарейки". Это ошибка: метка нужна
уже на ступени 1, а реестр - для разбора первого же инцидента.

## 6. Чего в конвейере нет

- **Автоматического отката по качеству ответов.** Судья, останавливающий выпуск
  сам себя, - плохая идея по той же причине, по которой judge-метрики не
  сделаны блокирующими.
- **Канареечного выпуска весов модели.** Закрыто расчётом полосы памяти, а не
  соображениями стоимости: ADR-0020, раздел "Контекст".
- **A/B-тестирования продуктовых гипотез.** На нашем объёме различие в
  конверсии не наберёт значимости за разумный срок. Это отличается от
  канарейки: там мы ищем поломку, здесь - улучшение.
- **Автоматического отката инфраструктуры.** Terraform применяется вручную с
  просмотром плана. Автоматическое применение на одном узле, где живут все
  хранилища, опаснее пользы.
- **Постмортемов как процесса.** Практика правильная, часов в смете этапа 1 на
  неё нет. Записано как долг эксплуатации - та же запись есть в
  [15-observability](15-observability.md).
