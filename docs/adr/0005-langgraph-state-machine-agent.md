# 0005. Строить агента как конечный автомат на LangGraph

- **Статус:** Принято
- **Дата:** 2026-08-20
- **Связанные требования:** FR-2.3, FR-2.4, BR-05, NFR-2.1, NFR-3.3, риски R-08, R-09

## Контекст

Требования задают не последовательность вызовов, а набор состояний с разными
условиями выхода. Запрос проходит проверку входа, планирование, извлечение
фактов, генерацию, проверку выхода. Из проверки входа есть выход в отказ (422),
из извлечения - в отказ по отсутствию данных, из проверки выхода - в отказ по
атрибуции. Число шагов извлечения заранее неизвестно и ограничено сверху.

Линейная цепочка промптов такую логику выражает только вложенными условиями в
коде приложения, и тогда состояние агента перестаёт быть наблюдаемым: в трассе
видно N вызовов модели, но не видно, в каком состоянии он находился и почему
перешёл дальше. Для системы, где отказ - штатный и требуемый исход (BR-05), это
неприемлемо.

Отдельное ограничение - предел итераций. Без явного максимума агент зацикливается
на вопросе, ответа на который в графе нет; в API это поле `max_steps` со
значением не более 6.

## Решение

Агент реализуется как явный конечный автомат на LangGraph StateGraph. Состояния
и переходы объявляются декларативно, предел шагов задаётся на графе, а не в
прикладном коде. Каждый переход попадает в трассу OpenTelemetry как отдельный
участок.

Диаграммы последовательности в `docs/diagrams/model.c4` разбиты по границам фаз
автомата, а не произвольно.

## Рассмотренные альтернативы

| Вариант                                                | Почему отклонён                                                                                                                                                                    |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Линейная цепочка промптов (LangChain LCEL)             | Ветвление и предел итераций выражаются только в прикладном коде, состояние не наблюдаемо в трассе                                                                                  |
| Собственный автомат без библиотеки                     | Даёт полный контроль, но требует своей реализации сохранения состояния, повторов и потоковой отдачи. Экономия на зависимости оплачивается работой, не входящей в ценность продукта |
| Фреймворк мультиагентной оркестрации (CrewAI, AutoGen) | Разделение на роли-агенты решает не нашу задачу: у нас один агент с несколькими инструментами. Добавляет недетерминированность там, где нужен предсказуемый набор переходов        |

## Последствия

- LangGraph - внешняя зависимость Python-экосистемы. Риска импортозамещения не
  создаёт: это библиотека в процессе приложения, а не серверный продукт, и на
  требования к реестру отечественного ПО не влияет.
- Автомат нужно поддерживать: добавление инструмента - это новое состояние и
  новые переходы, а не ещё один вызов в цепочке. Плата за наблюдаемость.
- Ограничение `max_steps` становится частью контракта API и попадает в
  спецификацию, а не остаётся настройкой развёртывания.
