# 0006. Взять Neo4j и Qdrant как графовое и векторное хранилища

- **Статус:** Предложено. Утверждается после ответа на Q-16
- **Дата:** 2026-08-20
- **Связанные требования:** FR-1.3, FR-3.1, NFR-3.1, NFR-1, вопрос Q-16, риск R-06

## Контекст

Решение [ADR-0004](0004-graphrag-over-vector-only-rag.md) требует двух хранилищ:
графового для сущностей и связей, векторного для входной точки поиска. Оба
попадают в диаграмму уровня 2, поэтому выбор фиксируется до начала разработки.

Определяющее ограничение задано [ADR-0002](0002-access-control-before-retrieval.md):
фильтр по грифу применяется в самом запросе, а не постобработкой. Для векторного
хранилища это означает фильтрацию по полезной нагрузке одновременно с поиском
ближайших соседей. Хранилища, где фильтр применяется после набора top-k,
непригодны принципиально: при узком доступе выдача схлопывается до пустой, а
полнота падает непредсказуемо (риск R-06).

Второе ограничение - закрытый контур: только то, что разворачивается
on-premise, без обращений наружу.

Третье ограничение пока неизвестно. Вопрос Q-16 о требованиях импортозамещения и
наличии в реестре отечественного ПО Заказчику ещё не задан. Neo4j - продукт
шведской компании и в реестре отсутствует. Это делает выбор условным.

## Решение

Графовое хранилище - Neo4j, векторное - Qdrant.

Статус записи - "Предложено". Утверждение переносится на этап обследования,
работа 1.5, после ответа на Q-16. Если Заказчик подтвердит требование реестра,
запись заменяется новой.

Чтобы условность не превратилась в переписывание системы, доступ к обоим
хранилищам инкапсулируется: агент обхода графа и агент векторного поиска на
диаграмме уровня 3 - единственные места, знающие о конкретной базе.

## Рассмотренные альтернативы

Графовое хранилище:

| Вариант                             | Почему отклонён                                                                                                                                                                         |
| ----------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ArangoDB                            | Совмещает документы, граф и вектор в одном продукте, что заманчиво. Но обход графа на глубину 3-4 заметно медленнее, а язык AQL менее выразителен для путевых запросов, чем Cypher      |
| Реляционная база с рекурсивными CTE | Не требует нового продукта в контуре, но каждая новая связь - миграция схемы, а разреженные связи "перепак" и "аналог" добавляются постоянно                                            |
| **Neo4j**                           | **Выбран.** Cypher выражает путевые запросы напрямую, метка ACL ставится атрибутом узла и уходит в предикат запроса, драйвер Bolt зрелый. Community-редакция разворачивается on-premise |

Векторное хранилище:

| Вариант                    | Почему отклонён                                                                                                                                                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| pgvector                   | Уже есть PostgreSQL для служебных данных, соблазн не плодить сущности. Но фильтрация по метаданным и поиск ANN плохо совмещаются: планировщик выбирает либо индекс по вектору, либо по метке, и на узком доступе полнота проседает |
| Elasticsearch / OpenSearch | Гибридный поиск из коробки и привычная эксплуатация, но существенно требовательнее к памяти при том же объёме                                                                                                                      |
| Milvus                     | Сопоставим по функциям, но тяжелее в развёртывании: отдельные координаторы и хранилище метаданных на объёме в 15 000 позиций не оправданы                                                                                          |
| **Qdrant**                 | **Выбран.** Фильтр по полезной нагрузке применяется вместе с поиском соседей, а не после. Российское происхождение снимает часть вопроса Q-16. Разворачивается одним контейнером                                                   |

## Последствия

- Два хранилища вместо одного: две системы в эксплуатации, две схемы бэкапа, две
  точки отказа. Признаётся сознательно - совмещённые решения проигрывают там, где
  у нас блокирующее требование.
- Гриф хранится дважды: атрибутом узла в графе и полем полезной нагрузки в
  векторе. Расхождение между ними означает утечку, поэтому проставление грифов
  вынесено в отдельную работу конвейера (3.3), а не размазано по загрузке.
- Neo4j Community не поддерживает горизонтальное масштабирование записи. На
  ожидаемом объёме это несущественно, но при кратном росте потребует либо
  коммерческой редакции, либо смены хранилища.
- Пока запись не утверждена, работа 3.1 не может считать выбор окончательным:
  инфраструктурный код пишется через абстракцию доступа к хранилищу.
