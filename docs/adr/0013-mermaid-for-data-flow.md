# 0013. Рисовать поток данных в Mermaid, компонентную модель оставить в LikeC4

- **Статус:** Принято
- **Дата:** 2026-09-13
- **Связанные требования:** [ADR-0003](0003-likec4-for-c4-model.md), [ADR-0011](0011-data-layer-lake-orchestrator-quality.md)

## Контекст

[ADR-0003](0003-likec4-for-c4-model.md) зафиксировал единственную нотацию для
диаграмм проекта: модель C4 описывается кодом на LikeC4, все представления
строятся из одной модели. Смысл ограничения - не допустить расхождения диаграмм
между собой при переименовании элемента.

Слой данных потребовал схемы другого рода. C4 описывает элементы и связи между
ними; поток данных описывает состояния одних и тех же данных и переходы между
ними. Зона озера - не контейнер: Bronze и Silver не два разных места, а два
состояния одного набора. Проверка качества - не компонент, а условие на ребре.
Уложить это в C4 можно, но получится диаграмма, где половина прямоугольников
означает не то, что означают остальные.

## Решение

Поток данных описывается отдельным файлом
[`data-pipeline.mmd`](../diagrams/data-pipeline.mmd) на Mermaid. Компонентная
модель остаётся в LikeC4 без изменений.

Граница между нотациями проводится по вопросу, на который отвечает диаграмма:

| Вопрос | Нотация |
| --- | --- |
| Из каких частей состоит система и кто с кем связан | LikeC4 |
| Что происходит с данными по пути от источника к ответу | Mermaid |

Точка стыковки одна и она названа явно: конвейер загрузки, сервис инференса и
оба хранилища присутствуют в обеих схемах под теми же именами. Если элемент
переименован в модели C4, его надо переименовать и в схеме потока - это ровно та
ручная работа, от которой ADR-0003 уходил, и её объём ограничен четырьмя
элементами сознательно.

## Рассмотренные альтернативы

| Вариант | Почему отклонён |
| ------- | --------------- |
| Добавить представление потока данных в model.c4 | Пришлось бы объявлять зоны озера и проверки качества элементами модели. Они появились бы и на уровне 2, где им не место, либо потребовали бы отдельной вложенной системы, существующей только ради одного представления |
| Нарисовать в drawio | Раскладка сохраняется, но диаграмма перестаёт быть текстом: правка не читается в diff. Та же причина, по которой в ADR-0003 отклонено рисование |
| Обойтись таблицей без схемы | Поток данных с ветвлением по результату проверки качества в таблице не читается. Кроме того, схема архитектуры данных - предмет сдачи домашней работы 5 |
| Перевести весь проект на Mermaid | Mermaid не поддерживает единую модель с несколькими представлениями: каждая диаграмма живёт отдельно, и переименование контейнера означает правку во всех семи. Это и есть проблема, ради которой выбран LikeC4 |

## Последствия

**Положительные.**

- Каждая схема отвечает на свой вопрос в подходящей нотации.
- Mermaid рендерится напрямую на GitHub, то есть схема потока читается в
  браузере без сборки.
- Обе нотации текстовые: правка видна в diff.

**Отрицательные.**

- **В проекте две нотации вместо одной.** Ограничение ADR-0003 ослаблено, и это
  надо называть так, а не "дополнено". Цена - ручная сверка четырёх общих
  элементов.
- **Расхождение схем ничем не проверяется.** LikeC4 валидирует свою модель,
  Mermaid не знает о её существовании. Автоматической проверки, что имена
  совпадают, нет; на текущем объёме она дороже самой сверки.
- **PNG собирается другим инструментом.** К экспорту LikeC4 добавляется
  mermaid-cli, то есть вторая цепочка сборки картинок со своими зависимостями.

## Условия пересмотра

Пересматривается, если число общих элементов между схемами превысит десять: с
этого объёма ручная сверка перестаёт быть надёжной и нужна либо генерация одной
схемы из другой, либо возврат к единой модели.
