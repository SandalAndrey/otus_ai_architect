# План работ (WBS)

Версия: 1.1. Основание: БФТ 1.1, реестр рисков, смета.

Работы разбиты на четыре фазы. Границы фаз совпадают с точками, где можно
остановиться без потери сделанного: это требование контрактной модели T&M с
ограничением стоимости.

## Соответствие фаз этапам договора

| Фаза                             | Этап договора           | Модель оплаты  |
| -------------------------------- | ----------------------- | -------------- |
| 1. Обследование и проектирование | Этап 0                  | Fixed Price    |
| 2. Проверка гипотез (PoC)        | Этап 0, вторая половина | Fixed Price    |
| 3. Разработка MVP                | Этап 1                  | T&M with a cap |
| 4. Готовность к эксплуатации     | Этап 1                  | T&M with a cap |

## Фаза 1. Обследование и проектирование

Результат: подтверждённые требования, золотой датасет, архитектурное видение.

| Код | Работа                                                          | Роль                       | Артефакт                |
| --- | --------------------------------------------------------------- | -------------------------- | ----------------------- |
| 1.1 | Интервью по опроснику, фиксация NFR с целевыми значениями       | Analyst                    | Дополненный БФТ         |
| 1.2 | Получение источников D-01, D-02, D-04, D-10, разведочный анализ | DS/ML                      | Отчёт о качестве данных |
| 1.3 | Золотой датасет: 50-100 пар вопрос-ответ                        | Analyst, эксперт Заказчика | Регрессионный набор     |
| 1.4 | Уточнение онтологии графа на реальных наименованиях             | DS/ML                      | Схема графа             |
| 1.5 | Выбор моделей, расчёт сайзинга, HLD (C4 уровни 1-2)             | Architect                  | HLD, ADR                |

Работа 1.3 лежит на критическом пути. Без датасета невозможны ни приёмка
качества (NFR-2), ни проверка гипотез в фазе 2: сравнивать результат не с чем.
Датасет создаётся с участием эксперта-товароведа Заказчика, поэтому его
выделение (вопрос Q-08) - блокирующее условие начала работ.

## Фаза 2. Проверка гипотез (PoC)

Результат: подтверждение или опровержение самых дорогих допущений.

| Код | Работа                                                             | Роль                | Артефакт               |
| --- | ------------------------------------------------------------------ | ------------------- | ---------------------- |
| 2.1 | Разрешение сущностей на выборке каталога (FR-1.4)                  | DS/ML               | Точность слияний       |
| 2.2 | Распознавание прайсов разного качества (FR-1.1)                    | DS/ML               | Доля успешного разбора |
| 2.3 | Фильтрация по ACL до извлечения на выбранной векторной БД (FR-3.1) | Backend             | Протокол проверки      |
| 2.4 | Прогон на золотом датасете, замер профиля A                        | DS/ML, QA           | Отчёт PoC              |
| 2.5 | Decision Gate                                                      | Architect, Заказчик | Решение                |

Три исхода Decision Gate: продолжаем в объёме MVP; сокращаем объём и
пересматриваем потолок; закрываем проект с оплатой фаз 1-2. Третий исход
предусмотрен намеренно. Если распознавание прайсов даёт менее 60 процентов или
разрешение сущностей требует ручного подтверждения более чем в половине
случаев, экономика не сходится, и узнать это дешевле здесь, чем на приёмке.

| Код | Работа                                                 | Роль               | Артефакт                   |
| --- | ------------------------------------------------------ | ------------------ | -------------------------- |
| 4.1 | Тест-план и тестовые случаи                            | QA                 | Тест-план                  |
| 4.2 | Сквозное тестирование и проверка разграничения доступа | QA                 | Протокол                   |
| 4.3 | Нагрузочное тестирование на профиле B                  | QA                 | Отчёт по латентности и RPS |
| 4.4 | Регрессионный прогон на золотом датасете               | QA, DS/ML          | Отчёт о качестве           |
| 4.5 | Вывод в эксплуатацию                                   | DevOps             | Работающая система         |

Работа 4.2 проверяет блокирующий критерий приёмки: пользователь без прав не
получает данные грифа Confidential. Отрицательный результат означает, что
система не принимается независимо от остальных показателей.

## Критический путь

```
1.3 Золотой датасет
 -> 2.4 Прогон PoC
 -> 2.5 Decision Gate
 -> 3.1 Инфраструктура
 -> 3.2 Конвейер загрузки и построение графа
 -> 3.4 Гибридный поиск и переранжирование
 -> 3.5 Агент как конечный автомат
 -> 4.4 Регрессионный прогон
 -> приёмка
```

Цепочка внутри фазы 3 определяется зависимостью по данным, а не порядком в
таблице. Пока не поднята инфраструктура, конвейеру некуда писать; пока граф не
построен, поиск не на чем проверять; пока поиск не работает, агенту нечего
вызывать. Регрессионный прогон требует работающей системы целиком, поэтому
идёт после 3.5, а не сразу после Decision Gate.

Вторая цепочка к приёмке идёт параллельно и короче, но обрывает её независимо
от первой:

```
3.6 Разграничение доступа и guardrails -> 4.2 Проверка разграничения -> приёмка
```

Она короче, но обрывает приёмку так же надёжно: 4.2 проверяет блокирующий
критерий. Поэтому 3.6 не имеет резерва по срокам, хотя и не лежит на основной
цепочке.

Остальные работы фазы 3 резерв имеют. Работа 3.3 (грифы и инкрементальное
обновление) идёт параллельно 3.4, работа 3.7 (интеграции) - параллельно 3.5,
работа 3.8 (наблюдаемость) завершается к 4.3.

Задержка золотого датасета сдвигает Decision Gate, всю фазу 3 и приёмку,
поэтому она вынесена в допущения договора.
