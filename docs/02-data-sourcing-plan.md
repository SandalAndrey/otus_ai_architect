# Приложение А. План обеспечения данными

**Приложение А. План обеспечения данными**

**К документу: Бизнес-функциональные требования (БФТ), версия 1.1**

Проект: Корпоративная платформа товарных знаний на базе мультимодального GraphRAG

Заказчик: интернет-магазин коллекционных масштабных моделей, более 15 000 позиций в наличии

Версия: 1.1 Статус: Черновик / на согласовании с Заказчиком

Дата: 11 августа 2026 г.

## А.1. Назначение документа

Документ определяет, какие данные проекта берутся из реальных источников Заказчика, какие замещаются синтетическими, и на каком основании принято каждое решение. Он же фиксирует перечень вопросов к Заказчику, ответы на которые влияют на архитектуру, а не на наполнение системы.

Документ решает три задачи: обосновать достоверность результатов приёмки, ограничить объём чувствительных данных, покидающих контур Заказчика, и защитить проект от типовой ошибки - демонстрации качества на искусственно чистом наборе.

## А.2. Принцип разделения

В основу положено следующее правило:

> **Реальными берутся данные, которые система анализирует. Синтетическими замещаются данные, которые система защищает.**

Обоснование. Риск качества сосредоточен в наименованиях, каталогах, прайсах и изображениях: именно их разбирает конвейер извлечения, и именно там синтетический набор подменяет результат - модель показывает высокую точность на искусственно однородных данных и теряет её на продуктиве.

Закупочные цены, договоры и персональные данные система не анализирует: она закрывает их грифом и обязана не выдать их пользователю без прав. Для проверки этого механизма содержимое узла безразлично - значение имеет только корректность метки и работа фильтрации на этапе выборки. Следовательно, реальные значения не дают выигрыша в достоверности приёмки, но создают риск раскрытия при публичной защите.

Из правила есть одно исключение - прайс-листы поставщиков, которые одновременно анализируются и подлежат защите. Порядок работы с ними описан в разделе А.4.

## А.4. Прайс-листы: реальный контейнер, синтетическое значение

Прайс-лист - единственный источник, который одновременно является объектом анализа и носителем коммерческой тайны. Разделение выполняется по полям, а не по файлам:

- От Заказчика запрашиваются подлинные файлы поставщиков без изменения вёрстки, включая экземпляры плохого качества. Сохраняются структура таблиц, колонтитулы, сноски, опечатки и артефакты сканирования - то есть всё, что нагружает конвейер извлечения.
- Колонка закупочной цены замещается синтетическим значением на этапе индексации, до записи в хранилище. Подмена выполняется отдельным шагом конвейера, факт подмены фиксируется в метаданных документа.
- Оценка качества извлечения при этом не страдает: проверяется способность конвейера найти и распарсить ячейку в её реальном окружении, а не корректность самого числа.

Альтернативный вариант, если Заказчик готов: запросить у поставщиков прайсы с уже удалённой ценовой колонкой. Он проще организационно, но хуже с точки зрения проверки, поскольку меняет вёрстку таблицы.

## А.5. Методика генерации синтетических данных

Синтетика должна воспроизводить статистическую форму реальных данных, а не только их формат. Набор, где все закупочные цены составляют ровно 60 % от розничной, не проверяет ни ранжирование, ни выявление аномалий.

| Поле            | Метод генерации                                                                                                               | Контроль правдоподобия                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Закупочная цена | Розничная цена x (1 - маржа), где маржа выбирается из распределения, заданного по группе брендов                              | Заказчик подтверждает диапазон маржи по группам, не раскрывая значений по конкретным позициям                     |
| Срок поставки   | Логнормальное распределение с параметрами по типу поставщика: отечественный, импортный, предзаказ                             | Медиана и хвост согласуются с фактическими сроками, названными заказчиком устно                                   |
| Договоры        | Публичный шаблон договора поставки, заполненный вымышленными реквизитами; спецификация формируется из реальных артикулов D-01 | Проверяется объём, структура разделов и наличие приложений - то, что влияет на чанкинг                            |

## А.6. Обезличивание обращений покупателей

Источник D-10 наиболее ценен для проекта и требует отдельной процедуры, поскольку содержит и полезное содержание, и персональные данные.

- Из выгрузки удаляются идентификаторы клиента, номера заказов, контактные данные и подписи. Обработка выполняется в контуре Заказчика до передачи исполнителю.
- Сохраняются формулировки вопроса, упоминания артикулов и наименований, а также признак эскалации и итог обращения - то, ради чего набор и запрашивается.
- Результат вычитывается вручную. Автоматическая маскировка на выборке такого объёма не даёт достаточной гарантии, а объём в 200-300 обращений допускает сплошную проверку.
- Из полученного набора формируется регрессионный комплект: не менее 50 вопросов с эталонными фактами, подтверждёнными экспертом-товароведом.

## А.9. Режим обращения с данными

### А.9.1. Ограничения (обязательны к исполнению)

- Реальные персональные данные, реальные закупочные цены и подлинные тексты договоров не попадают в репозиторий проекта ни в каком виде, включая тестовые фикстуры, примеры в документации, снимки экрана и кэш промежуточных артефактов.
- Репозиторий передаётся преподавателю и остаётся в портфолио на неопределённый срок. Любые данные в нём следует считать опубликованными.
- Обработка данных выполняется в закрытом контуре. Передача содержимого во внешние сервисы, включая сервисы распознавания и перевода, исключена.
- При аренде внешнего GPU (профиль B по NFR-1) на арендованный узел передаётся только обезличенный либо синтетический набор, и только при положительном ответе на вопрос Q-10.

### А.9.2. Организация хранения

- Наборы данных разделяются на два каталога: реальные данные и синтетические. Каталог реальных данных целиком исключается из системы контроля версий.
- В репозиторий помещаются генераторы синтетики и схемы данных, но не сами наборы. Это обеспечивает воспроизводимость без переноса содержимого.
- Каждый набор сопровождается паспортом: источник, дата получения, режим по настоящему приложению, применённые преобразования, срок хранения.
- Демонстрационное видео записывается на наборе, прошедшем проверку по вопросу Q-09.

## А.10. Порядок применения

- До начала PoC: провести интервью по разделу А.7, получить источники D-01, D-02, D-04 и D-10, зафиксировать ответы в протоколе и при необходимости выпустить версию 1.1 настоящего приложения.
