# Прототип мультиагентного онлайн-пути

Проверяет схему из [ADR-0007](../../docs/adr/0007-multiagent-online-path.md) и
параметры извлечения из [документа о конвейере](../../docs/12-rag-pipeline.md)
на синтетическом срезе каталога. Это первый код проекта: он не MVP, а
измерительный инструмент для профиля A (CPU).

Что проверяется:

- передача задач между супервизором и агентами, включая параллельный запуск
  векторного поиска и обхода графа;
- адаптивная маршрутизация: класс A против класса B, разница в числе вызовов
  модели;
- фильтр по грифу в самой выборке, а не после неё - один и тот же вопрос при
  разных грифах даёт разный результат;
- время каждого шага извлечения, чтобы понять, что на CPU узкое место.

## Запуск

Зависимости уже стоят в локальном виртуальном окружении. Из каталога прототипа:

```powershell
.venv\Scripts\Activate.ps1
python app.py --demo
```

По умолчанию модель подменяется детерминированной заглушкой, а эмбеддинги
берутся настоящие. Так проверяется маршрут агентов, не завися от вероятностного
вывода модели.

С живой моделью:

```powershell
$env:LLM_PROVIDER = "ollama"
$env:LLM_MODEL    = "qwen3-8b"
python app.py --demo
```

Отдельный вопрос и свой набор грифов:

```powershell
python app.py "Какие ещё бренды выпускали эту модель по той же пресс-форме" --acl public
python app.py "Какая закупочная цена по IXO-2101-BL" --acl public,internal,confidential
```

## Переменные окружения

| Переменная     | Значения         | По умолчанию                | Зачем                             |
| -------------- | ---------------- | --------------------------- | --------------------------------- |
| `LLM_PROVIDER` | `stub`, `ollama` | `stub`                      | Заглушка или локальный endpoint   |
| `LLM_BASE_URL` | URL              | `http://localhost:11434/v1` | OpenAI-совместимый адрес          |
| `LLM_MODEL`    | имя              | `qwen3-8b`                  | Модель в Ollama                   |
| `LLM_MODEL_<РОЛЬ>` | имя          | значение `LLM_MODEL`        | Своя модель под роль: `SUPERVISOR`, `VECTOR`, `GRAPH`, `COMPOSER`, `VERIFIER` |
| `EMBEDDER`     | `bge`, `hash`    | `bge`                       | `hash` отключает загрузку bge-m3  |
| `RERANKER`     | `bge`, `off`     | `bge`                       | `off` пропускает переранжирование |

Сочетание `EMBEDDER=hash RERANKER=off LLM_PROVIDER=stub` запускается за секунду
и не требует ни одной модели: годится, чтобы проверить логику после правки.

## Отчёт по вызовам модели

После прогона печатается разбивка по ролям: число вызовов, время, входные и
выходные токены, скорость и счётчик ответов, в которых модель рассуждала.

Последний столбец существует не для полноты. Время ответа само по себе не
отличает "модель тяжёлая" от "режим рассуждений не выключился": и то, и другое
даёт десяток секунд на короткий JSON. Гибридные модели Qwen3 рассуждают по
умолчанию, переключатель `/no_think` подставляется и в системный промпт, и в
пользовательский ход, но сработал ли он - видно только по непустому блоку
`<think>` в ответе. Если счётчик ненулевой, замер латентности недействителен.

Отсюда же смысл `LLM_MODEL_<РОЛЬ>`. Классификация вопроса и выбор глубины обхода
возвращают короткий JSON, там достаточно модели поменьше; качество нужно только
составителю ответа. Разделение заложено в
[ADR-0007](../../docs/adr/0007-multiagent-online-path.md) и проверяется так:

```powershell
$env:LLM_MODEL           = "qwen3-4b-instruct"
$env:LLM_MODEL_COMPOSER  = "qwen3-8b"
python app.py --demo
```

Отдельно полезно прогнать всё на `qwen3-4b-instruct`: это вариант Instruct,
режима рассуждений у него нет вовсе, поэтому он служит контролем. Если время на
вызов упадёт вдвое - дело в размере модели; если вчетверо - на 8B рассуждения
всё-таки шли.

## Состав

| Файл           | Что внутри                                               | Соответствие модели C4                   |
| -------------- | -------------------------------------------------------- | ---------------------------------------- |
| `app.py`       | Граф LangGraph, узлы агентов и компонентов, CLI          | Уровень 3 целиком                        |
| `llm.py`       | Единственная точка обращения к модели, заглушка и Ollama | Клиент инференса                         |
| `retrieval.py` | Эмбеддинги, гибридный поиск, RRF, переранжирование       | Агент векторного поиска, переранжировщик |
| `knowledge.py` | Синтетический каталог: чанки с грифами, граф знаний      | Векторное хранилище, граф знаний         |

Разделение на агентов и детерминированные компоненты в коде такое же, как на
диаграмме: `guard_in`, `guard_out`, `rerank_node` работают по правилу,
остальные узлы обращаются к модели.

## Данные

Реальные данные Заказчика в репозиторий не попадают (раздел А.9 плана
обеспечения данными). Набор в `knowledge.py` придуман, но воспроизводит три
свойства, ради которых строится система:

- **перепаки**: три позиции разных брендов по одной пресс-форме `T-VAZ2101` -
  связь, которая векторным поиском не находится;
- **алиасы**: ВАЗ-2101, Жигули, Lada 1200, копейка - одна сущность;
- **смешанный гриф в одном документе**: в прайсе поставщика наименование
  позиции публично, а закупочная цена и маржа закрыты.

Последнее и есть демонстрация ADR-0002. Вопрос про закупочную цену с грифами
`public,internal` и с `public,internal,confidential` даёт разный ответ, причём
в первом случае закрытый чанк не извлекается вовсе, а не отбрасывается после.

## Чего в прототипе нет

- Qdrant и Neo4j заменены структурами в памяти. Выбор хранилищ пока имеет
  статус "Предложено" ([ADR-0006](../../docs/adr/0006-neo4j-and-qdrant-as-stores.md)),
  и привязываться к ним рано.
- Разреженная часть гибридного поиска реализована своим BM25, а не разреженным
  вектором bge-m3: ради одного поля тянуть весь стек FlagEmbedding не стоит.
  На качество сравнения это не влияет, на архитектуру - тем более.
- Потоковой отдачи ответа нет: она относится к контракту API, а не к схеме
  агентов.
- Трассировка печатается в консоль, а не уходит в OpenTelemetry.
